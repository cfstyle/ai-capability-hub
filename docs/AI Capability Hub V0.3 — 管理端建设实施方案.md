# AI Capability Hub V0.3 — 管理端建设实施方案

**项目名称：** 企业级 AI 业务能力中心  
**当前基线：** V0.2.2  
**目标版本：** V0.3  
**阶段定位：** 管理控制台与开发者接入能力建设  
**部署方式：** Docker Compose（支持完全离线部署）

---

## 一、建设目标

### 1.1 总体目标

在 V0.2.2 已有 MCP 聚合能力的基础上，建设独立的 Web 管理端，使平台具备可视化管理、服务注册、工具发现、能力发布、受控调试及运行审计能力。

第一版应实现：

**开发人员无须修改 Hub Core 代码，仅通过浏览器，即可完成独立 MCP Server 的注册、测试、发布和管理。**

管理端是 Hub 控制面的可视化入口，而不是重新开发 MCP Gateway。

### 1.2 核心原则

1. **不重构现有 Gateway。** 优先复用当前 FastMCP 聚合及路由实现。
2. **前后端分离。** 管理端通过标准 REST API 访问 Hub Core。
3. **真实数据驱动。** 所有页面状态来自后端，不使用模拟业务数据充当实际结果。
4. **开放接入。** 不限制 MCP Server 使用的开发语言与框架。
5. **控制面与执行面隔离。** 管理端不得绕过 Hub 治理链直接调用敏感业务工具。
6. **安全优先。** 服务注册、调试、发布、停用等操作均需要相应权限和审计。
7. **控制首版范围。** 优先解决 MCP 开发人员的真实接入与管理需求，不建设完整企业应用市场。

## 二、技术架构

### 2.1 技术选型

| 组件 | 选型 |
|---|---|
| 前端框架 | Vue 3 + TypeScript |
| 构建工具 | Vite |
| UI 组件 | Element Plus |
| 状态管理 | Pinia |
| 路由 | Vue Router |
| HTTP 客户端 | Axios 或 Fetch 封装 |
| 管理后端 | 复用 FastAPI |
| MCP 聚合 | 保留现有 FastMCP 实现 |
| 数据存储 | SQLite（MVP） |
| 前端部署 | Nginx 静态资源容器 |
| 整体部署 | Docker Compose |

若现有代码已实现等效的技术组件，优先复用，不应为了统一选型重复开发。

### 2.2 推荐部署结构

```text
                 企业内网
                    │
             ┌─────────────┐
             │  Hub Admin  │
             │  Vue3 SPA   │
             └──────┬──────┘
                    │ REST API
                    ▼
          ┌──────────────────────┐
          │       Hub Core       │
          │                      │
          │  Management API      │
          │  Registry            │
          │  Governance          │
          │  Audit               │
          │  MCP Gateway         │
          └──────────┬───────────┘
                     │
              Streamable HTTP
                     │
          ┌──────────┴───────────┐
          ▼                      ▼
      TICM MCP              Message MCP
      Python                Node.js
```

Agent Harness 使用 `/mcp`。

管理控制台使用 `/api/v1/*`。

两个入口拥有独立的身份认证和权限策略。

### 2.3 前端部署策略

推荐单独的 `hub-admin` 容器。

通过 Nginx 将前端请求与管理 API 统一在一个受控访问域名下：

- `/`：管理端静态资源。
- `/api/v1/*`：代理至 Hub Core 管理 API。
- `/mcp`：保留独立的 MCP 客户端访问路径。

不依赖外部 CDN、在线字体、第三方脚本或公网运行时资源。

## 三、管理端功能设计

### 3.1 首页：运行总览

展示以下信息：

- 已注册 MCP Server 总数。
- 已启用及已停用服务数量。
- 已发布 Tool 数量。
- 服务在线及异常状态。
- 最近调用次数、成功与失败数量。
- 最近异常及服务变更记录。

所有统计必须来自真实注册记录和调用记录。

当前不存在的监控指标，不得使用模拟数据填充；应显示未启用或暂无数据。

### 3.2 MCP Server 管理

**优先级：P0，必须实现。**

主要功能：

1. 查询已注册 MCP Server。
2. 按名称、所属业务系统、状态、维护人搜索。
3. 注册新的远程 MCP Server。
4. 编辑服务名称、描述、维护人等元数据。
5. 测试服务连接。
6. 主动刷新并发现工具。
7. 启用、停用服务。
8. 查看工具数量、服务版本及最近检查结果。
9. 查看服务异常信息。
10. 对不再使用的服务执行受控注销。

服务详情至少包括：

| 字段 | 说明 |
|---|---|
| Server ID | 平台唯一标识 |
| Server Name | 服务名称 |
| Endpoint | MCP 服务地址 |
| Transport | Streamable HTTP |
| Version | 服务版本 |
| Description | 业务说明 |
| Owner | 维护人员 |
| Environment | 所属环境 |
| Status | 当前状态 |
| Tool Count | 已发现工具数量 |
| Last Checked | 最近检查时间 |

注册必须采取先验证、后发布的方式。

### 3.3 工具目录管理

**优先级：P0，必须实现。**

自动展示 MCP Server 提供的 Tools。

每项工具包含：

- 唯一工具标识。
- 所属 MCP Server。
- 工具名称及业务描述。
- Input Schema。
- Output Schema（服务提供时）。
- 风险等级。
- 是否启用。
- 当前发布状态。
- 最近发现时间及契约版本。

工具详情页应支持 JSON Schema 查看，必要时提供格式化视图和原始 JSON 视图。

工具命名冲突必须在发布前阻止。

### 3.4 工具在线调试

**优先级：P0，必须实现。**

提供类似 API 调试工具的交互体验。

操作流程：

1. 选择 MCP Server。
2. 选择 Tool。
3. 根据 Input Schema 自动生成参数表单。
4. 输入测试参数。
5. 校验参数类型及必填项。
6. 提交受控测试调用。
7. 展示调用状态、执行耗时、返回结果及错误信息。
8. 生成可查询的调用审计记录。

参数表单优先支持：

- string
- number / integer
- boolean
- enum
- object
- array

对于复杂嵌套结构，可以提供 JSON 编辑模式。

**安全约束：**

V0.3 默认仅允许管理员调试已批准的 Mock 工具和明确标记为安全只读的工具。

写入、删除、审批、发送消息等具有副作用的 Tool，不得因为管理端具备“执行”按钮就自动获得调用权限。

如需执行此类工具，必须先具备独立的授权和确认机制。

### 3.5 调用日志与审计

**优先级：P1，必须在 V0.3 验收前完成。**

支持：

- 按时间范围查询。
- 按 Server、Tool、执行结果过滤。
- 查看请求关联 ID。
- 查看执行耗时、错误类型。
- 查看调用主体及授权结果。
- 查询服务注册、发布、停用等管理操作。

敏感请求参数、账号、令牌及业务数据必须进行脱敏或限制记录。

禁止把原始凭据展示在浏览器或普通日志中。

### 3.6 系统管理

**优先级：P1。**

第一版仅提供：

- 管理员登录与退出。
- 当前用户与权限信息。
- Hub 运行状态。
- 版本信息。
- 基础配置查看。
- 管理操作审计。

初期可采用受控的本地管理员身份机制，后续预留统一身份认证接口。

不得在前端代码中硬编码管理员密码或长期有效密钥。

## 四、MCP Server 注册与发布流程

建议明确以下生命周期：

```text
创建注册记录
      ↓
连接测试
      ↓
自动发现 Tools
      ↓
工具契约及风险检查
      ↓
待发布
      ↓
管理员发布
      ↓
已发布 / 可调用
      ↓
停用 / 更新 / 注销
```

### 4.1 注册阶段

开发人员录入服务信息后，Hub 验证服务地址、传输协议及认证配置。

必须防止用户通过任意 URL 注册访问不应访问的内部管理地址、回环地址或云元数据服务。

### 4.2 工具发现

连接测试通过后，由 Hub 使用 MCP Client 读取工具定义。

保存本次发现的工具清单及 Schema 快照。

发现成功不等于自动发布。

### 4.3 发布阶段

发布前完成：

- 服务标识唯一性检查。
- 工具命名冲突检查。
- 基础 Schema 校验。
- 风险等级登记。
- 访问权限校验。
- 服务连接状态检查。

通过后才允许工具进入 Hub 的正式可调用目录。

### 4.4 更新阶段

工具刷新发现 Schema 变化时：

- 保存新版本快照。
- 比较工具名称、参数及返回结构的差异。
- 未通过审核前，不直接替换已发布契约。
- 如果实际上游已经发生不兼容变化，应阻止受影响调用，不能继续以旧契约盲目执行。

### 4.5 停用阶段

停用操作必须真正影响 Gateway。

要求：

- 新请求不能继续执行已停用工具。
- 已有运行中请求按照确定的取消或完成策略处理。
- 停用记录写入审计。
- 不删除历史调用记录。

如果当前 FastMCP 挂载机制无法原生完成运行时热更新，可先采用受控的配置刷新或重载策略。

但管理端必须展示操作是否实际生效，不能仅仅修改数据库状态就提示发布成功。

## 五、REST 管理 API 需求

首先审查现有 `hub-core/src/api/`，已具备的接口直接复用，缺少的再补充。

建议统一前缀：

`/api/v1`

### 5.1 服务管理

| Method | Endpoint | 功能 |
|---|---|---|
| GET | `/servers` | 分页查询服务 |
| POST | `/servers` | 创建注册记录 |
| GET | `/servers/{id}` | 服务详情 |
| PATCH | `/servers/{id}` | 修改服务信息 |
| POST | `/servers/{id}/test` | 测试连接 |
| POST | `/servers/{id}/discover` | 刷新工具定义 |
| POST | `/servers/{id}/publish` | 发布服务 |
| POST | `/servers/{id}/disable` | 停用服务 |

### 5.2 工具管理

| Method | Endpoint | 功能 |
|---|---|---|
| GET | `/tools` | 分页查询工具 |
| GET | `/tools/{id}` | 工具详情 |
| POST | `/tools/{id}/test` | 受控测试调用 |
| PATCH | `/tools/{id}/policy` | 修改工具治理策略 |

### 5.3 审计与系统

| Method | Endpoint | 功能 |
|---|---|---|
| GET | `/audit-logs` | 查询审计记录 |
| GET | `/dashboard/summary` | 首页统计 |
| GET | `/system/status` | 查看运行状态 |
| GET | `/auth/me` | 当前管理员信息 |

以上是建议的目标 API 契约，并不表示这些接口目前已经存在。

管理 API 应提供明确的参数 Schema、分页规则、状态码和错误响应。

建议生成 OpenAPI 文档，作为前端与后端联调的唯一接口依据。

## 六、管理端数据持久化

V0.3 继续采用 SQLite。

至少需要管理以下数据实体：

| 实体 | 用途 |
|---|---|
| MCPServer | 服务注册记录 |
| MCPTool | 工具元数据 |
| ToolSnapshot | 工具定义及版本快照 |
| ToolPolicy | 工具授权与风险策略 |
| ServerStatus | 服务检查结果 |
| InvocationLog | 工具调用审计 |
| AdminAuditLog | 管理操作审计 |

必要时扩展管理员账号及权限表。

所有数据库结构变更必须通过版本化迁移执行，禁止依赖删除数据库重建来完成普通升级。

必须验证 Docker Compose 容器重启、重新创建后注册记录仍然存在。

## 七、管理端 UI 设计规范

整体采用简洁、专业的企业管理系统风格。

### 7.1 导航结构

```text
AI Capability Hub
│
├── 总览
│
├── MCP 服务
│   ├── 服务列表
│   └── 服务详情 / 注册
│
├── 工具目录
│   ├── 工具列表
│   └── 工具详情 / 调试
│
├── 调用审计
│
└── 系统管理
    ├── 运行状态
    └── 管理员信息
```

### 7.2 设计要求

- 默认浅色界面。
- 减少无意义的统计卡片和装饰。
- 页面以数据表格、搜索过滤及详情面板为核心。
- 支持中文界面。
- 操作状态清晰区分：未注册、待发布、已发布、已停用、异常。
- 危险操作需要明确确认。
- 服务地址及长 Schema 应可查看和复制。
- 空数据、加载中、连接失败有明确状态。
- 不使用模拟指标制造平台繁忙或成熟的假象。

界面可以参考成熟的 API Gateway、服务注册中心及开发者平台，不需要重新发明复杂交互。

## 九、开发阶段与任务拆分

### P1-A：现有后端能力审查

检查：

- Registry 是否真实持久化。
- 动态注册是否实际生效。
- 工具发现是否保存 Schema。
- Gateway 是否支持停用后阻止调用。
- 管理 API 是否已有相应接口。
- 调用日志是否可查询。
- 是否已有管理员身份验证。

**交付：** API 能力清单、缺口清单、数据模型确认结果。

### P1-B：完善管理 API

实现服务注册、连接测试、工具发现、发布停用、日志查询和基础认证等缺失功能。

**交付：** 可测试的管理 REST API、OpenAPI 文档及自动化测试。

### P1-C：开发管理端基础界面

完成：

- 前端工程。
- 登录及路由。
- 基础布局。
- 总览页面。
- MCP Server 列表与详情。
- 服务注册表单。

**交付：** 可以连接真实后端数据的管理端。

### P1-D：实现工具目录与调试

完成：

- Tool 自动发现展示。
- Schema 查看。
- Schema 驱动的动态参数表单。
- 只读 Mock Tool 调用。
- 执行结果与错误展示。

**交付：** 可用的工具调试台。

### P1-E：治理与运维能力

完成：

- 服务启用与停用。
- 工具发布状态。
- 基础风险标识。
- 调用审计。
- 管理操作审计。
- 服务健康状态。

**交付：** 基本可运维的 Hub 管理平台。

### P1-F：集成、离线部署与验收

完成：

- Docker Compose 集成。
- 镜像离线打包验证。
- 前后端联调。
- 重启持久化测试。
- 负面安全测试。
- 端到端测试和用户验收。

**交付：** V0.3 可部署版本及验收报告。

## 十、最终验收标准

### 功能验收

- [ ] 可通过浏览器访问管理端。
- [ ] 管理员可以登录、退出。
- [ ] 可以注册新的远程 MCP Server。
- [ ] 可以测试服务连接。
- [ ] 可以自动发现并展示 Tools。
- [ ] 可以查看 Tool Schema。
- [ ] 可以通过动态表单调试安全的 Mock Tool。
- [ ] 可以发布和停用服务。
- [ ] 发布与停用能够实际影响 Gateway。
- [ ] 可以查询真实的调用日志。
- [ ] 注册与工具定义在容器重启后仍然存在。

### 架构验收

- [ ] 管理端通过 REST API 操作，不直接修改数据库。
- [ ] 管理端不直接调用下游业务 MCP。
- [ ] 新增服务不需要修改 Hub Core 代码。
- [ ] Python 和 Node.js MCP 均能通过管理端注册。
- [ ] 管理端与 MCP Gateway 权限分离。
- [ ] 现有 Harness 调用功能保持兼容。

### 安全验收

- [ ] 未认证用户无法进入管理功能。
- [ ] 非管理员不能注册或发布服务。
- [ ] 未经批准的工具不能通过调试台执行敏感操作。
- [ ] 服务注册地址受到安全限制。
- [ ] 敏感凭据不在前端或日志中明文暴露。
- [ ] 管理操作能够追溯到实际操作主体。

### 部署验收

- [ ] Docker Compose 启动成功。
- [ ] 断网环境能够完成部署。
- [ ] 容器重启不丢失注册数据。
- [ ] 服务异常有明确反馈。
- [ ] 原有 MCP 聚合服务正常运行。

## 十一、明确不属于 V0.3 的内容

以下功能暂不建设：

- 企业 MCP 插件商城。
- 容器镜像在线安装与托管。
- MCP Server 自动生成工具。
- 完整 OAuth / SSO 企业身份平台。
- 复杂的多级审批流。
- 全行多租户权限中心。
- 多环境统一发布流水线。
- Skills 市场。
- Agent 管理及编排。
- 多语言开发 SDK。
- 复杂的实时大屏与监控报表。

如现有后端已经具备其中某项能力，可以保留，不要求删除；但不能因此扩大本阶段交付范围。

## 十三、给开发执行方的核心要求

**优先实现真实可用的管理闭环，不要优先追求页面数量。**

开发过程中必须：

- 首先阅读现有 Hub Core 代码，不能只根据 README 推测实现。
- 优先复用已有 Registry、Gateway 和 Governance。
- 不修改现有 MCP 业务工具的协议和调用行为。
- 不通过硬编码 Mock 数据完成管理端验收。
- 前端必须调用真实管理 API。
- 不擅自实现本方案明确排除的功能。
- 遇到 FastMCP 动态注册或代理限制时，先定位并给出兼容方案，避免大规模重构。
- 每个阶段完成后执行回归测试，确保原有 MCP 调用能力不受影响。

**V0.3 成功标准：**

一个未参与 Hub Core 开发的技术人员，可以独立通过管理端注册自己的 MCP Server，查看并测试其工具，在通过必要审核后发布到 Hub，使 Agent Harness 能够正常发现和调用。

这意味着 AI Capability Hub 从一个技术验证工程，正式具备了向多人协作、插件化接入和企业业务能力生态演进的基础。
