# AI Capability Hub V0.2 评审意见与 V0.2.1 修订决策

这份评审报告质量较高。我建议采纳全部 6 项必须澄清的问题，其中 5 项需要落实为具体架构决策，第 3 项涉及的 Session 设计需要按照最新 MCP 协议重新表述。

此外，15 条意见中有三处我建议调整，而不是直接照搬：

1. 聚合网关模式：完全采纳。 Hub 应当对 Harness 表现为一个完整的 MCP Server，内部再充当多个 MCP Server 的客户端。

2. Stateless：采纳，但必须区分新旧协议。 MCP `2026-07-28` 已取消协议级 Session 和 `initialize` 握手，而 `2025-11-25` 等旧版本仍保留相关机制。不能简单认为所有 Streamable HTTP 服务天然无状态。

   [image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

   GitHub+1

3. 工具健康检查：建议修正。 临时故障不宜立即从工具目录删除，否则可能影响 Agent 的工具缓存和执行计划。更合理的是标记服务不可用、调用时返回明确错误，只有被正式停用或因安全风险隔离时才取消工具暴露。

这次评审还有一个重要意义：它说明我们最初提出的架构理念基本成立，但已经到了必须明确技术决策和接口契约的阶段。

V0.2.1 不应该增加更多功能，而应该消除 V0.2 中那些会导致开发人员作出不同理解的模糊边界。

## 一、V0.2.1：六项核心技术决策

下面这些决策可以直接作为原总体方案的补充内容。

| 编号      | 评审问题         | 最终建议                                                    |
| ------- | ------------ | ------------------------------------------------------- |
| ADR-001 | Hub Core 技术栈 | Python 3.11+、官方 MCP SDK 2.x、FastAPI/ASGI、HTTPX、Pydantic |
| ADR-002 | Gateway 模式   | 聚合 MCP Server，不采用单纯 HTTP 透传                             |
| ADR-003 | Session 管理   | Hub 优先无状态；对需要会话的旧版下游，由独立 MCP Client 适配                  |
| ADR-004 | MVP 身份授权     | 测试阶段使用签名测试令牌；真实业务接入前必须完成可信身份委托                          |
| ADR-005 | 工具发现与缓存      | 注册时发现、启动时校验、管理员主动刷新，契约变化先审核                             |
| ADR-006 | 协议兼容         | 以 `2026-07-28` 为基线，按实际测试决定旧版兼容范围                        |

### ADR-001：Hub Core 选择 Python

这次我倾向于明确选择 Python，而不是继续交给实施团队自由决定。

原因是你熟悉 Python、FastAPI，后续主要维护者很可能也是你。官方 Python MCP SDK 2.x 已经提供 MCP Server、Client 和新旧协议兼容能力。

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub+2



建议技术组合：

| 组件       | 选型                            |
| -------- | ----------------------------- |
| 编程语言     | Python 3.11+                  |
| MCP 协议处理 | 官方 `mcp` SDK 2.x              |
| 管理 API   | FastAPI                       |
| HTTP 服务  | ASGI + Uvicorn                |
| 下游网络访问   | HTTPX，优先使用 SDK 提供的 MCP Client |
| 数据校验     | Pydantic                      |
| 注册与配置存储  | SQLite（MVP）                   |
| 初始配置     | YAML                          |
| 部署       | Linux 容器，支持 Windows 开发调试      |

但 Hub 采用 Python，不代表各个 MCP Server 必须使用 Python。

这是本项目的基本架构原则，不应发生变化。

### ADR-002：Hub 必须作为聚合 MCP Server

我完全同意评审方的建议。

Hub 对外应该是一个标准 MCP Server，对内则是多个业务 MCP Server 的客户端。

DeepSeek Harness

只需配置一个 Hub MCP 地址

Hub Aggregator

tools/list → 汇总并过滤工具目录

tools/call → 授权、路由、调用、审计

TICM MCP

OA MCP

邮件 MCP

这里还需要额外定义一个重要边界：

第一版只聚合 MCP Tools，不聚合 Resources、Prompts，也不支持复杂的反向调用和交互式协议扩展。

这样可以大幅减少首版需要处理的协议复杂度。

后续再增加其他 MCP 能力类型。

### ADR-003：无状态设计，但不假设所有下游无状态

最新 MCP `2026-07-28` 协议已经取消了协议级 Session。官方 Python SDK 2.x 同时支持新旧协议版本。

[image](https://www.google.com/s2/favicons?domain=https://blog.modelcontextprotocol.io\&sz=32)

Model Context Protocol Blog+1



因此我建议：

- Hub 对外优先采用 `2026-07-28` 无状态协议。
- Hub 业务执行和用户授权独立于 MCP 连接状态。
- 下游使用新协议时，采用独立请求模式。
- 下游使用旧协议时，由 MCP Client 适配器管理其初始化及必要的会话状态。
- 不自行编写一套复杂的 Session 复用和协议翻译引擎。

但是要明确：无状态不能解决所有跨版本问题。

例如旧版服务依赖服务器主动发起请求、采样或者交互式确认时，不能假设普通 `tools/call` 代理可以完整兼容。

这类工具应当标记为暂不支持，不能静默降级。

### ADR-004：MVP 身份认证与正式业务认证分两阶段

评审方指出的问题非常准确。

我建议明确区分：

P0—P2：模拟业务阶段

使用本地测试身份签发的短期签名令牌，至少包含两个不同的测试主体。

DeepSeek Harness 在请求 Hub 时通过 `Authorization: Bearer ...` 传递令牌。

Hub 验证令牌，从可信声明中获取用户身份和权限，不相信模型传入的员工编号。

下游 MCP Server 使用独立的测试凭据。

P3：接入真实 TICM

必须完成正式认证方案，包括用户身份来源、业务系统授权映射和服务间安全凭据。

如果不能建立真实用户与 TICM 权限的可信关系，就不能声称已经实现生产级用户数据隔离。

同时禁止将 Hub 接收到的 Bearer Token 不加验证地直接转发给 TICM。MCP 官方安全规范明确指出了这种 Token Passthrough 的风险。

DeepSeek Harness 的 MCP 客户端支持自定义 HTTP 请求头，因此测试身份令牌的传递具有实现基础；但你本机安装版本的实际配置方式仍应在 P0 验证。

### ADR-005：工具发现与缓存

我同意评审建议，首版不需要复杂的服务发现系统。

建议采用：

注册时

Hub 连接 MCP Server，读取工具定义及 Schema

服务启动时

检查已注册服务与批准版本是否一致

管理员刷新时

重新读取工具，并比较契约变化

检测变更时

生成新版本快照，未经审核不替换已发布契约

Harness 查询时

返回当前用户授权可见的工具目录

这里还需要增加一条：工具缓存必须区分授权范围。

不能把管理员看到的全部工具目录缓存下来，直接返回给普通员工。

MCP 新版协议已经提供 `ttlMs` 和 `cacheScope` 缓存控制。对于权限不同的工具目录，应采用私有缓存语义。初期甚至可以将缓存 TTL 设为零，以减少权限变更后产生过期可见性的问题。

### ADR-006：协议兼容边界

我建议明确为：

| 协议版本                  | V0.2.1 策略 |
| --------------------- | --------- |
| `2026-07-28`          | 首选支持      |
| `2025-11-25`          | 条件兼容，必须测试 |
| `2025-06-18`          | 作为后续兼容候选  |
| `2025-03-26`          | 暂不承诺      |
| `2024-11-05` HTTP+SSE | 首版不支持     |

这里有一个非常重要的区别：

官方 SDK 支持某个协议版本，不代表我们开发的聚合逻辑能够无损代理该协议的所有功能。

因此 P0 必须建立实际的客户端—Hub—下游 Server 兼容性矩阵。

首版只承诺通过实际测试的 `tools/list` 和 `tools/call` 功能，不宣称完整兼容所有 MCP 扩展。

## 二、补充协议调用时序

这是评审方提出的另一个重要交付物。

下面是建议的 V0.2.1 工具调用流程。

一次完整工具调用

Harness

1\. 请求 tools/list

携带客户端认证信息

Hub Registry

2\. 返回授权工具目录

使用已批准的工具快照

Harness

3\. 发起 tools/call

传入业务工具名和参数

Hub Governance

4\. 校验身份、工具权限、参数

不通过直接拒绝

下游 MCP

5\. 执行业务能力

通过自身适配器访问授权业务接口

Hub Gateway

6\. 校验并返回执行结果

记录审计，保留业务错误信息

对于第一版而言，我们只需要确保这条链路完整成立。

不需要同步开发 Agent 调度、长任务管理、Skills 编排等模块，因为这些已经属于 Harness 或业务服务自身的职责。

## 三、其余九项优化建议，我的处理意见

| 评审项        | 处理决定                                              |
| ---------- | ------------------------------------------------- |
| 7. 架构图     | 采纳。部署图、调用时序图、注册流程图纳入技术设计                          |
| 8. 工具命名    | 采纳 `service_id__tool_name`，并制定稳定、可逆的命名映射规则；冲突拒绝注册 |
| 9. 健康检查    | 修改。采用与版本匹配的协议探测，不固定使用 MCP ping                    |
| 10. 错误规范   | 采纳。区分协议错误、治理拒绝、上游业务错误，敏感错误不直接透传                   |
| 11. 配置管理   | 采纳 SQLite + YAML Bootstrap                        |
| 12. 工期及依赖  | 采纳依赖分析；开发工时需在 P0 验证环境和授权条件后估算                     |
| 13. 多环境    | 采纳。开发、测试、生产环境隔离，环境信息属于注册元数据                       |
| 14. 审计存储   | 采纳结构化日志；保留期限按银行适用制度确定，不预设统一六个月                    |
| 15. SSE 推送 | 暂不支持进度流式转发，首版同步等待并设置调用超时                          |

其中需要特别提醒第 9 项：

MCP `2026-07-28` 已经移除了旧版 `ping` 方法，所以不能将 MCP ping 作为所有服务统一的健康检查方式。新版可以使用 `server/discover` 或其他适当的只读协议探测，旧版则按照对应生命周期处理。也不能简单用 HTTP GET `/mcp` 是否返回 200 判断，因为新协议的远程传输以 POST 为基础。

对于错误体系，我建议内部统一分类，但不要在协议层随意创造不符合 MCP 的响应格式。协议和路由错误使用合法的 JSON-RPC 错误；业务工具执行失败则保留 MCP Tool Result 的错误语义，并附上经过脱敏的业务错误信息。

## 四、第一版还要再增加一个限制：只支持“可代理的 MCP 工具”

这是评审没有明确提出，但我认为现在应该补充的内容。

并非所有第三方 MCP Server 都能在聚合网关后面无损运行。

例如有些工具可能依赖：

- 复杂的用户交互或客户端回调。
- 长时间流式任务。
- 特定客户端扩展。
- 下游私有 Session 状态。
- 自定义认证或特殊资源操作。

这些问题不应成为首版 MVP 的负担。

我建议在服务注册时进行兼容性检查，把接入结果明确区分为：

可接入

标准工具发现与调用，认证和协议测试通过

有限兼容

部分工具可用，其他扩展需要额外适配

暂不支持

存在无法满足的协议、身份或安全要求

这样可以确保“开放接入”不是“任何 MCP Server 都无条件注册成功”。

这是企业级产品应有的边界。

## 五、下一步的实际执行顺序

我建议这次评审之后，不要急着进入 P1，而是把 P0 拆成几个非常具体的任务：

1. 确认技术基线：Python、官方 MCP SDK 2.x、FastAPI、SQLite，确定并锁定实际依赖版本。
2. 验证 DeepSeek Harness：确认本机版本的 Streamable HTTP、协议协商和认证 Header 能力。
3. 验证聚合代理：使用两个独立模拟 MCP Server，完成 `tools/list` 聚合与 `tools/call` 路由。
4. 验证新旧协议适配：先保证当前协议，再根据实际需要测试旧版本。
5. 验证权限边界：使用两个测试用户、两组不同权限，确保授权工具目录与工具执行都正确隔离。
6. 确认 TICM 接口条件：并行申请或确认授权测试环境和只读 API，避免后期项目被业务接口权限阻塞。

P0 的完成标准要比原方案更严格：

只有一个 Harness 能够通过 Hub 正确调用两个独立 MCP Server，并且权限隔离、工具发现、路由和错误处理都通过测试，才允许进入真实 TICM 集成。

## 最后还有一条架构原则，我建议写进 V0.2.1

Hub Core 负责标准化接入和统一治理，不负责替所有 MCP Server 实现其内部业务逻辑。

它同样不应该承担所有协议扩展的复杂兼容工作。

未来如果某位同事开发了一个 Java MCP Server，那么他应该只需要遵守公开的接入契约，就可以把能力发布到 Hub。

如果他使用的是比较特殊的 MCP 扩展，那就需要通过专门的适配器或等待 Hub 支持对应扩展，而不是直接修改 Hub 核心代码。

这能同时满足你最关心的两件事情：

一是未来不因某个 Harness 或 SDK 变化而推翻整个项目；二是其他开发人员可以独立贡献自己的业务能力，而不用共同维护一套复杂的核心工程。

因此，我认为这份评审的最终处理结果应该是：

V0.2 架构方向不变；升级为 V0.2.1，补全技术选型、聚合代理、协议兼容、身份授权、工具缓存和错误治理决策。

这轮修订之后，开发团队已经可以按照明确的技术边界进入 P0 验证，不需要再进行大规模概念讨论。
