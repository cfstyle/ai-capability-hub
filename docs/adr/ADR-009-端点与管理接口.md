# ADR-009：端点路由架构与管理接口认证隔离

**状态：** 已批准  
**日期：** 2026-11-12  
**决策者：** 项目组  

## 背景（Context）
- Hub Core 既需要作为 MCP 网关接收 Agent 客户端的工具调用流量，又需要提供管理 API 供管理员执行服务注册、元数据配置、状态更新与契约刷新，同时还需要向监控系统提供健康检查接口。
- 需要确定不同端点的进程部署形态、路由划分及各自的安全认证边界。

## 决策（Decision）
1. **进程与路由架构：**
   - MVP 阶段采用“同容器、同进程、不同路由”的单体服务架构。
   - 路由分配明确：
     - `/mcp`：标准 Streamable HTTP 协议端点，供 DeepSeek Harness 等 Agent 客户端进行协议握手与工具调用。
     - `/api/v1/*`：RESTful 管理端点，供运维管理员执行服务注册、更新、下线与工具手动刷新。
     - `/healthz`：进程存活检查（Liveness probe），供容器运行时探测应用状态。
     - `/readyz`：就绪检查（Readiness probe），探测 SQLite 存储与核心依赖就绪状态。
2. **认证体系严格分离：**
   - `/mcp` 端点校验客户端及终端用户的授权令牌（JWT）。
   - `/api/v1/*` 管理端点采用独立的管理员鉴权机制（如 Admin API Key 或专用的管理员签名令牌）。
   - 严禁将管理员 API Key 用于工具调用鉴权，严禁普通客户端使用 JWT 调用管理注册接口。
3. **网络与安全隔离：**
   - 生产环境中，管理端点 `/api/v1/*` 必须结合网络访问控制列表（ACL）、反向代理限制或运维专用子网进行二次访问隔离。
4. **服务演进设计：**
   - 路由与契约保持规范，未来若管理后台流量增大或有独立审计要求，可在不改变外部调用契约的前提下，无缝拆分为独立的管理微服务与网关微服务。

## 影响（Consequences）
- **正面影响：**
  - MVP 阶段架构简洁，单进程极大降低了内网单机或容器部署与运维复杂度。
  - 端点职责明确，流量与认证机制清晰隔离，杜绝高低权限凭据混用风险。
- **负面影响：**
  - 同进程运行管理 API 与 MCP 网关，在高并发场景下管理操作可能对网关产生偶发 CPU/IO 争抢，需依托异步 FastAPI 事件循环并做好超时保护。
