# ADR-004：MVP 身份认证与分阶段授权模型

**状态：** 已批准  
**日期：** 2026-11-12  
**决策者：** 项目组  

## 背景（Context）
- 银行系统对数据隔离、主体权限与审计追溯有极为严格的安全合规要求。
- 大模型 Agent 具有不可控的生成特性，不能信任模型在自然语言 Prompt 或工具入参中传入的员工工号或机构参数。
- 客户端与服务端间若直接透传上游 Token（Token Passthrough），会带来凭据泄露与权限扩散的安全隐患。
- MVP 初期缺乏完整的企业统一身份委托平台，需在快速技术验证与安全底线之间取得平衡。

## 决策（Decision）
1. **多层身份判定原则：**
   - 严格区分“客户端/Agent 身份”、“实际登录用户身份”、“工具服务身份”与“实际业务操作主体”。
   - 严禁通过大模型生成的参数判定数据权限，必须从受信任的传输层请求头（如 `Authorization: Bearer <token>`）中解析并验证身份主体声明。
2. **两阶段演进策略：**
   - **P0～P2 阶段（模拟业务与框架验证）：** 使用本地预置密钥签发的短期测试 JWT（签名测试令牌），配置至少两个不同权限范围的测试主体（如普通员工与投资经理），模拟严格的权限隔离。下游 Mock MCP Server 使用内部独立的测试凭据。
   - **P3 阶段（真实业务接入）：** 在接入 TICM 真实系统前，必须建立可信的正式身份委托机制（如通过企业 IAM / OAuth2 委托授权或短期业务凭证兑换），将终端用户可信身份安全映射为业务系统许可权限；若无法建立真实委托，禁止接入真实生产数据。
3. **禁止 Token 透传（Anti-Token-Passthrough）：**
   - 禁止将 Hub 接收到的客户端 Authorization Bearer Token 不加校验地直接透传给下游业务 MCP Server。
   - Hub 与下游 MCP Server 之间采用独立受控的服务间调用凭据，或基于受校验用户上下文签发的专用受限凭据。

## 影响（Consequences）
- **正面影响：**
  - 从机制上杜绝了通过 Prompt 提示词注入篡改身份和越权访问业务数据的漏洞。
  - 符合 MCP 官方安全最佳实践，避免了上游客户端凭据向不可信内网服务扩散。
  - P0-P2 保持开发敏捷度，P3 坚守银行生产安全底线。
- **负面影响：**
  - P3 阶段对接真实业务系统时，需要跨部门协调接入企业级身份委托基础设施，存在一定的联调周期。
