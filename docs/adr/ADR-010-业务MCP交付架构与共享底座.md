# ADR-010：自研业务 MCP 服务交付架构与通用运行底座（mcp-runner）

**状态：** 已批准  
**日期：** 2026-11-20  
**决策者：** 项目组  

---

## 背景（Context）

1. **业务自研占比高**：预计未来 80% 以上的下游 MCP 服务由团队自主开发，并统一放置在 `services/` 目录下集中管理与演化。
2. **内网高频迭代的发布痛点**：若采用传统的“每次业务代码变更/新增都全量重构 Docker 镜像”方式，在高频迭代场景下，需要频繁执行 `docker build`、`docker save`、拷贝几百 MB 甚至数 GB 的 `.tar` 镜像至隔离内网、再执行 `docker load`。流程繁琐、耗时长，严重制约开发与调试效率。
3. **微服务与依赖冲突平衡**：业务 MCP 服务数量多，若揉入单体大镜像会导致依赖地狱与爆炸半径放大；但若为每一个简单的 Python MCP 服务都独立维护完整的 Docker 构建与发布流水线，运维成本过高。

---

## 决策（Decision）

决定采用 **“统一反向代理 + 通用微胖底座（mcp-runner）+ 业务代码外挂 + 三层依赖保障”** 的交付架构。

### 1. 通用运行底座（mcp-runner:latest）
- **单镜像复用**：针对自研 Python 类的 MCP 服务，只构建一个通用的轻量基础镜像 `mcp-runner:latest`（约 300MB）。
- **底座内建能力**：预装 `fastmcp`、`uvicorn`、`httpx`、`pydantic`、`sqlalchemy`、`redis` 等覆盖 80%~90% 日常业务场景的核心依赖。
- **零额外镜像构建**：所有在 `services/` 下的新增 Python MCP 服务，全部在 `docker-compose.yml` 中复用该镜像，**禁止为纯业务逻辑的 Python MCP 单独打应用镜像**。

### 2. 源码外挂与秒级发布（Volume Mount）
- 业务代码存放于宿主机的 `services/<mcp-name>/`。
- 容器启动时通过卷挂载（`-v ./services/<mcp-name>:/app`）载入代码。
- **发布规范**：日常业务逻辑更新或修复 Bug，仅需内网同步/覆盖宿主机源码，由服务内部进程（如 `uvicorn --reload`）自动热重载生效，耗时控制在秒级，无需重启容器或重打镜像。

### 3. 三层依赖演化保障机制
针对业务新增第三方 Python 库（底座未包含）的场景，制定三层递进的离线处理规范：

1. **第 1 层：底座预设（预防式）**
   - 制作 `mcp-runner` 时纳入常见协议库、数据库驱动与数据解析工具，尽可能在源头杜绝新增依赖。
2. **第 2 层：全局共享依赖池（宿主机外挂）**
   - 宿主机创建 `/data/shared-packages` 目录，通过卷挂载映射至各容器。
   - 容器环境变量注入 `PYTHONPATH=/shared-packages:$PYTHONPATH`。
   - 当需要引入跨服务共用的通用库时，在内网宿主机执行一次离线 `pip install --target=/data/shared-packages xxx.whl`，所有容器即刻获得该库，无须重启镜像。
3. **第 3 层：服务级独立离线自安装（启动 Hook）**
   - 宿主机提供离线包仓库挂载 `/data/wheels`。
   - 针对单个服务的专属特殊依赖，容器启动命令配置检测机制：若检测到 `/app/requirements.txt` 存在未安装项，自动基于本地离线 wheel 目录进行安装。

---

## 影响（Consequences）

- **正面影响：**
  - **交付粒度极小**：交付物由数 GB 的 Docker 镜像变为几十 KB 的 Python 源码，极大简化内网拷贝与审批流程。
  - **开发体验跃升**：新增 MCP 服务无需编写 Dockerfile，只需在 compose 文件中声明服务与端口，数秒内即可上线。
  - **依赖统一治理**：避免各个业务各自为政打包导致的镜像膨胀与磁盘资源浪费，底层共享相同的 Python 运行时。
- **负面影响与应对：**
  - **运行期环境漂移风险**：通过将底座镜像锁定语义化版本号（如 `mcp-runner:v1.0.0`），并在宿主机规范化管理 `/data/shared-packages` 和 `/data/wheels` 目录，确保环境变更具备可追溯性。
