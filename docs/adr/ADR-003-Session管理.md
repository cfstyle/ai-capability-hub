# ADR-003：MCP 无状态设计与旧版下游会话管理

**状态：** 已批准  
**日期：** 2026-11-12  
**决策者：** 项目组  

## 背景（Context）
- MCP 规范在 `2026-07-28` 版本中进行了重大演进，取消了协议级 Session 与显式 `initialize` 握手机制，远程 Streamable HTTP 趋向于纯无状态请求/响应模型。
- 然而，部分旧版 MCP 服务（如 `2025-11-25` 规范）仍然依赖基于会话的连接管理和握手状态。
- Hub 面向外部 Agent 客户端与内部各业务下游时，需要明确其会话与连接状态的管理原则。

## 决策（Decision）
1. **Hub 对外无状态：**
   - 面向 Agent 客户端（如 DeepSeek Harness），Hub 优先采用 MCP `2026-07-28` 无状态协议规范。
   - Hub 业务执行、权限校验和调用审计与 MCP 连接状态完全解耦，每次调用基于 HTTP 请求头中的认证凭据独立判定。
2. **下游异构会话适配：**
   - 下游服务支持新版无状态协议时，采用独立 HTTP 请求交互。
   - 下游服务若依赖旧版有状态协议（如 `2025-11-25`），由 Hub 内部专用的 MCP Client 适配层维护连接生命周期、完成握手及必要的会话状态维持，对外部屏蔽会话细节。
3. **避免过度设计：**
   - Hub 不自行研发通用的协议级 Session 状态同步与复用引擎。
4. **不支持特性的显式拦截：**
   - 若旧版下游服务依赖服务端主动发起请求、采样或交互式客户端确认，普通 `tools/call` 代理无法无损适配。此类工具直接标记为“暂不支持”，禁止静默降级或吞没错误。

## 影响（Consequences）
- **正面影响：**
  - Hub 对外天然具备水平伸缩和无状态容器化能力，运维简单可靠。
  - 清晰隔离了新旧协议差异，避免旧版有状态机制污染整个网关架构。
- **负面影响：**
  - 针对旧版有状态下游，需要在 Client 适配层维护长连接池与保活逻辑，增加了一定的适配内存占用与生命周期管理复杂度。
