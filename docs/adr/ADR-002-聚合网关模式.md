# ADR-002：聚合 MCP Server 模式与能力边界

**状态：** 已批准  
**日期：** 2026-11-12  
**决策者：** 项目组  

## 背景（Context）
- 银行内网存在多个异构业务系统的 MCP Server（如 TICM 资金系统、OA、邮件等）。
- 若让外部 Agent 客户端（如 DeepSeek Harness）直接连接分散的多个下游 MCP Server，会导致客户端配置繁琐、网络暴露面增大、认证与权限控制分散。
- 需要在“单纯 HTTP 反向代理/透传”与“语义级聚合 MCP Server”之间确立网关架构模式，并定义首版的能力范围边界。

## 决策（Decision）
1. **聚合网关模式：** Hub 采用“聚合 MCP Server”模式。
   - 对外（面向 Agent 客户端）：Hub 表现为一个标准的单端点 MCP Server。
   - 对内（面向下游业务服务）：Hub 充当多个业务 MCP Server 的标准 MCP Client。
2. **核心调用链路处理：**
   - `tools/list`：Hub 负责向下游所有激活状态的 MCP Server 汇总工具列表，执行统一命名空间转换（`{service_id}__{tool_name}`）、检测重名冲突，并基于当前调用主体的权限策略过滤后返回。
   - `tools/call`：Hub 负责拦截请求，完成主体认证、工具级鉴权、风险检查与审计流水记录，然后将调用路由派发至对应下游 MCP Server，对返回结果进行安全脱敏与校验后回传客户端。
3. **能力范围收敛（MVP 边界）：**
   - 第一版（MVP）**只聚合 MCP Tools**，不聚合 Resources 和 Prompts。
   - 暂不支持复杂的反向调用（如采样 Sampling、Roots）和交互式协议扩展，大幅降低首版协议处理复杂度。

## 影响（Consequences）
- **正面影响：**
  - Agent 客户端配置极简，只需接入 Hub 单一地址即可获取企业全量授权能力。
  - 集中实施统一认证、工具级授权、调用审计与命名治理，避免下游直接暴露于不可信网络环境。
- **负面影响：**
  - Hub 成为调用链路的核心中枢节点，需要承担协议转换与代理转发开销，对网关性能和稳定性提出更高要求。
  - 首版不支持 Resources 和 Prompts 聚合，若业务系统依赖该类能力需留待后续版本扩展。
