# ADR-007：聚合实现路径：FastMCP 优先验证与退回预案

**状态：** 已批准  
**日期：** 2026-11-12  
**决策者：** 项目组  

## 背景（Context）
- 实现聚合 MCP 网关有两种主要技术路径：
  - **路径 A：** 基于独立 `fastmcp` 框架的高级能力（`create_proxy()`、`mount()`、Middleware、Provider 等）进行聚合与拦截。
  - **路径 B：** 基于官方 `mcp` SDK 2.x（如 `MCPServer` / `Client`）手工自研底层协议路由与分发聚合层。
- 需要特别注意：独立 `fastmcp` 框架与官方 `mcp` SDK 2.x 不是同一个项目。FastMCP 的部分默认行为（例如默认转发客户端 HTTP Header / Authorization）可能违反银行安全合规原则。

## 决策（Decision）
1. **P0 阶段优先验证路径 A（FastMCP `create_proxy + mount`）：**
   - 利用 FastMCP 将远程下游 MCP Server 转换为代理，并挂载至主 Server。
   - 利用父级 Middleware 拦截工具发现和工具执行，评估统一鉴权与审计的可行性。
2. **设立四大准入验证标准（决策门槛）：**
   - **工具发现：** 能否可靠地根据当前用户权限过滤 `tools/list` 响应。
   - **工具执行：** 每次 `tools/call` 能否被拦截并进行独立的用户鉴权与结构化审计。
   - **动态接入：** 能否在不重启服务和不修改核心代码的情况下，动态完成服务的注册与工具更新。
   - **身份隔离：** 能否显式禁用客户端 Authorization Header 的默认下游透传，防止凭证扩散和身份混用。
3. **退回与降级预案：**
   - 若 FastMCP 满足四项标准，正式确立为 Hub 聚合基础框架。
   - 若功能基本满足但存在个别接口限制，开发轻量受控适配层扩展。
   - 若授权拦截、动态注册或身份隔离存在不可克服的缺陷，果断退回路径 B，基于官方 `mcp` SDK 2.x 自研聚合路由与分发逻辑。
4. **架构解耦要求：**
   - 无论选择哪条路径，Registry 元数据、Governance 策略和路由配置必须由 Hub 自行定义与持久化，禁止与 FastMCP 内部对象强耦合，确保具备随时替换聚合底座的能力。

## 影响（Consequences）
- **正面影响：**
  - 若 FastMCP 验证通过，可大幅减少基础网关代理的代码编写工作量，加速交付。
  - 设立了严谨客观的准入标准，有效规避框架技术选型风险。
- **负面影响：**
  - P0 验证阶段需要编写专门的测试用例验证 FastMCP 边界行为；若触发退回预案，需在 P1 阶段补充自研聚合层开发工作量。
